AI Factory Plan: Paperclip + NVIDIA OpenShell on On-Prem OpenShift
1. Goal
Give each developer an "AI factory": a deployment on our on-prem OpenShift cluster where multiple coding agents work for hours to build a project end to end.
One factory per developer.
Each factory is 2–3 pods, not a pod per agent (cluster resources are limited).
Air-gapped environment: internal LLM endpoints, internal Git, mirrored container registry, Keycloak/AD for identity.
Separate OpenShift clusters for non-prod, stress and prod; cross-cluster traffic goes through a WAF.
2. Tool choices
Tool	Role in this plan	Decision
Paperclip (`paperclipai/paperclip`, MIT)	Control plane: tasks, agent assignment, heartbeats, budgets, approval/review gates, multi-company	Use. One Paperclip pod per factory.
NVIDIA OpenShell (`NVIDIA/OpenShell`, Apache-2.0)	Secure runtime: kernel-level sandboxing, per-binary network policy, credential injection, inference routing	Use. One long-lived sandbox per factory holds all agents.
OpenCode	Coding agent harness running inside the sandbox	Default harness. Supports custom providers via env config, so it can point at internal LLMs.
Sandcastle (`mattpocock/sandcastle`)	TypeScript library for scripting sandboxed agent runs	Not needed. Paperclip + OpenShell cover its role.
Key fact behind the design: by default, Paperclip runs agents as subprocesses inside its own container, with its filesystem and credentials. Budgets limit spend, not access. OpenShell supplies the missing isolation.
3. Architecture
3.1 Cluster-wide (installed once per cluster: non-prod, stress, prod)
OpenShell gateway in its own namespace (`openshell`). Control plane for sandbox lifecycle, policy, providers/credentials. Installed with the Helm chart; 1 replica.
Agent Sandbox controller + CRDs (`kubernetes-sigs/agent-sandbox`), required by OpenShell before its chart is installed. Cluster-scoped, so OpenShift admins must install it.
Keycloak OIDC for user authentication to the gateway (the chart's mTLS is transport only, not user auth).
3.2 Per factory (one namespace per developer)
Pod	Contents
Paperclip pod	Paperclip server + UI + embedded Postgres on a PVC. Holds Paperclip's own secrets. Custom image with the `openshell` CLI added.
OpenShell supervisor pod	Created by the gateway. Enforces policy, runs the egress proxy, injects credentials.
Agent sandbox (workload) pod	All of the factory's OpenCode agents, each in its own git worktree. `/sandbox` on a PVC so it survives restarts.
Paperclip dispatches work to the agents over SSH into the sandbox, using a Paperclip "Environment" of type SSH.
3.3 Why this split
Paperclip's DB and secrets are in a different pod from the agents, out of their reach.
The LLM key never enters the sandbox: agents call a local inference endpoint and OpenShell injects credentials only for approved endpoints.
Network rules match on destination and calling binary, so different tools in one sandbox can have different reach.
One sandbox for all agents is acceptable because everything in a factory belongs to one developer and one project.

4. Key design decisions
Namespaces are pre-created by the platform team, not by the gateway. Install the gateway without namespace-scoped resources, then install OpenShell's separate workspace chart into each factory namespace (it owns only the sandbox ServiceAccount, Role, RoleBinding and NetworkPolicy). The gateway then never needs cluster-wide namespace-create rights.
One gateway per cluster. Factories never send control traffic through the WAF, and non-prod problems can't affect prod.
Git is the shared state between agents. Each agent works in its own worktree and branch; merges go through the lead agent or Paperclip review gates. Agents should commit often, because in-memory state is lost on pod restart.
Store provider credentials as Kubernetes Secrets in a dedicated namespace (OpenShell's Kubernetes Secrets credential driver), not in the gateway DB.
Disable telemetry in both OpenShell (`server.telemetryEnabled=false` / `OPENSHELL_TELEMETRY_ENABLED=false`) and Paperclip (`PAPERCLIP_TELEMETRY_DISABLED=1` or `DO_NOT_TRACK=1`).
5. Implementation steps (non-prod pilot)
Step 1: Cluster prerequisites (OpenShift admins)
Verify the CNI enforces ingress and egress NetworkPolicy in sandbox namespaces (OVN-Kubernetes should). Test egress blocking from a pod.
Mirror images into the internal registry: OpenShell gateway, supervisor, sandbox runtime, Agent Sandbox controller.
Install the Agent Sandbox controller and CRDs; confirm pods in `agent-sandbox-system` are running.
Install the OpenShell gateway via Helm (`oci://ghcr.io/nvidia/openshell/helm-chart`) into namespace `openshell`:
`global.image.registry` → internal mirror
OIDC → Keycloak
telemetry disabled
workspace resources disabled on the gateway release (namespaces are pre-created)
Check the Agent Sandbox controller and OpenShell supervisor pods pass OpenShift Security Context Constraints (SCCs).
Step 2: Build two images
Agent sandbox image: OpenCode, git, language toolchains, SSH support.
Paperclip image: Paperclip (Node.js 24.11+) plus the `openshell` CLI. Must run as an arbitrary non-root UID, per OpenShift's default.
Step 3: Onboard one factory namespace (make this a repeatable pipeline)
Create namespace, e.g. `factory-<dev>`.
Apply ResourceQuota (caps total CPU/memory for the factory).
Install the OpenShell workspace chart into the namespace.
Create a long-lived sandbox (`--keep`) with:
PVC for `/sandbox`
network policy allowing only internal Git
inference routed to the internal LLM through OpenShell
CPU/memory limits sized for several concurrent agents
Deploy the Paperclip pod in the same namespace:
ReadWriteOnce PVC for the data directory (Postgres, files)
authenticated mode (not trusted-local), exposed via a Route
`automountServiceAccountToken: false`
default-deny ingress NetworkPolicy; allow only the router to port 3100
Git token scoped to the developer's project repos only
per-factory budget configured in Paperclip
In Paperclip, add an SSH Environment pointing at the factory sandbox and set it as the default for the factory's agents.
Step 4: Validate with one developer and 2–3 agents
Try to break the policy: curl an external host, try to read the LLM key, try to reach another factory's sandbox.
Measure CPU/memory per agent during builds and test runs; set realistic limits.
Confirm agents keep working across a sandbox pod restart (PVC + frequent commits).
6. Confirmed vs inferred
Confirmed in documentation:
Paperclip runs agents as subprocesses of its container by default; supports multi-company, git worktree execution workspaces, budgets, approval gates, and SSH "Environments".
OpenShell on Kubernetes: per sandbox, the gateway creates a Sandbox resource, supervisor and workload pods, a Service, NetworkPolicy and workspace PVC. Requires the Agent Sandbox controller and a CNI that enforces ingress/egress NetworkPolicy.
OpenShell supports namespace per workspace, split gateway/workspace Helm releases, OIDC user auth, image mirroring via `global.image.registry`, and a Kubernetes Secrets credential driver.
OpenShell sandboxes support SSH (`openshell sandbox ssh-config`, `sandbox exec`).
Network policy matches destination + calling binary; credentials are injected only for approved endpoints.
Inferred, must be verified in the pilot:
Paperclip's SSH Environment can reach an OpenShell sandbox through the gateway (Paperclip pod needs the `openshell` CLI + gateway credentials).
Paperclip can run multiple concurrent agents over one SSH environment, each in its own worktree.
OpenShell RBAC can restrict each factory's Paperclip to only its own sandbox, so dev A can't reach dev B.
A gateway outage pauses new work across all factories while running agents continue.
7. Risks and maturity
OpenShell Helm chart is marked experimental: "do not use in production". Keep in non-prod.
Paperclip Environments are documented under the experimental section.
Single gateway replica is a single point of failure per cluster (chart says leave at 1 unless testing multi-replica).
All agents share one sandbox: one runaway agent can starve the others; sandbox crash stops all; any approved policy expansion applies to all agents in it.
Fallback if SSH-through-gateway fails: write a custom Paperclip sandbox-provider plugin that calls the OpenShell TypeScript SDK. Paperclip plugins register an `environmentDriver` of kind `sandbox_provider`. Daytona, Modal and E2B providers are examples to copy.
Simpler fallback if OpenShell is blocked entirely: run Paperclip and agents in one hardened pod (restricted-v2 SCC, OpenShift EgressFirewall allowing only LLM + Git, no SA token, tightly scoped secrets). This loses per-binary policy and credential hiding.
